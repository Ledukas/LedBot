# LedBot — Known Issues / TODO

Compiled from user reports + a full code review of `LedBotCode.py`, `Functions.py`, and `cogs/giveaway.py`. Each item has a suspected/confirmed root cause and file:line reference.

## Reported by user

- [x] **Weekly GP report sometimes sends twice.** `on_ready` calls `bot.loop.create_task(run_at_specific_time())` on *every* firing (`LedBotCode.py:659`), with no re-entrancy guard — unlike `baba_ping`, which is protected by the `baba_task` flag (`LedBotCode.py:656-658`). `on_ready` fires again after any gateway reconnect/resume, not just on first startup, so each reconnect spins up another parallel copy of the Saturday-2AM loop. If two (or more) copies are alive by the time Saturday 2AM rolls around, `GP_weekly_auto()` fires once per copy — this is almost certainly the double-send. **Fixed:** replaced the hand-rolled loop with a `discord.ext.tasks.loop`, started once in `on_ready` behind an `is_running()` guard — a reconnect can no longer spawn a duplicate copy.

- [x] **Spiketrap ping stops working at random.** `baba_ping()` (`LedBotCode.py:546-557`) has no `try/except` anywhere in its infinite loop. `guild`, `baba_role`, and `baba_channel` are also only resolved once, right when the task starts (`LedBotCode.py:547-549`), not re-fetched each iteration. Any single failure — `baba_channel.send()` hitting a transient Discord API error/rate limit, the role or channel briefly not being in cache when the task starts (making `baba_role`/`baba_channel` `None`), etc. — raises an unhandled exception that kills the `asyncio` task permanently. Nothing restarts it, so the ping silently stops until the bot process is restarted. **Fixed:** the whole loop body is now wrapped in `try/except` (logs and keeps looping instead of dying), and `guild`/`baba_role`/`baba_channel` are re-resolved and null-checked every pass instead of being cached once at task start.

- [x] **No error text for `!assign`.** There actually is a local handler (`@assign.error`, `LedBotCode.py:626-635`), but the command body itself isn't defensive: if the given `game_name` doesn't match any row, `game` is `None` and `game[2]` on the next line (`LedBotCode.py:301-302`) throws a raw `TypeError`, which the handler reports back to Discord as `"An error occurred while processing the command: 'NoneType' object is not subscriptable"` — technically "text", but not helpful to a moderator. Fix: check `if game is None:` after the lookup and send a clear `"No game member found with name '{game_name}' in {IOguild}"` message instead of letting the raw exception surface. Also see the global-handler bug below — depending on discord.py's dispatch order this may be part of why some `!assign` failures look silent. **Fixed:** `assign` now validates `IOguild` against `guilds_data` and checks the game-name lookup for `None`, replying with which name was not found (and a nudge to run `!members_game` if they only just joined) instead of letting a raw `TypeError` reach the handler.

## Other bugs found in review

- [x] **Global error handler silently swallows unrecognized exceptions.** `on_command_error` (`LedBotCode.py:636-648`) only handles `MissingRole`, `MissingRequiredArgument`, `BotMissingPermissions`, `UserInputError`, and `CommandOnCooldown` (the last of which is explicitly `pass`ed). There is no `else` branch and no logging. Any command *without* its own local `.error` handler — that's every command except `assign` (`kick`, `invite`, `members_discord`, `members_guild`, `sync_counters`, `promotions`, `backup`, `mygains`, `giveaway`, etc.) — fails **completely silently** on any error type not in that list: no Discord message, no console/log output. This is very likely the biggest source of "it just didn't do anything" reports. **Fixed:** the handler now falls back to a generic "Something went wrong running that command. Ask a dev to check the bot logs." message and prints a full traceback to stderr, so an unexpected failure is never silent in both places at once. The known cases live in one ordered `logic.EXPECTED_COMMAND_ERRORS` table (ordered because `MissingRequiredArgument` is a subclass of `UserInputError`), with `logic.is_unexpected_command_error` deciding whether to log. Two things surfaced while fixing it: `MissingAnyRole` is **not** a subclass of `MissingRole`, so every `has_any_role` command (`wb-now`, `wb-next`, `gemdrop`) was silently rejecting unauthorized users and is now covered; and `CommandNotFound` had to be added as explicitly-silent, or the new catch-all would make the bot reply to every mistyped `!` message. The handler also now returns early for commands that have their own `@cmd.error` handler (only `assign`), since discord.py dispatches to both and the user would otherwise get two replies.

- [x] **`!led_stop` is probably broken.** It calls `await bot.logout()` (`LedBotCode.py:87`), but `Bot.logout()` doesn't exist in discord.py 2.x (the version pinned in `requirements.txt`) — it was replaced by `bot.close()`. This command likely raises `AttributeError` every time it's used (and, per the bug above, may fail silently). **Fixed:** now calls `bot.close()`. Confirmed: `Bot.logout()` does not exist in discord.py 2.3.1, so this raised `AttributeError` every time -- and, per the handler bug above, did so silently.

- [x] **Hardcoded year in `Functions.py:127`.** `new_column_names = {column: column.replace('GP2026_', '') for column in column_names_int}` hardcodes `2026`. Once the calendar rolls to 2027, this `.replace()` stops matching anything, so GP columns stop getting their year-prefix stripped — this breaks the formatted headers/output in `!mygains` and the red-GP report (and silently, since nothing errors — it just prints ugly/wrong column names). **Fixed:** now strips each column's own `GP{year}_` prefix via regex (`re.sub`) instead of a literal year — this also fixes a subtler version of the same bug that a naive "use `datetime.now().year`" fix wouldn't have caught: the 4 tracked columns (this week + 3 weeks back) can genuinely span two different calendar years near a year boundary (e.g. early January's "3 weeks ago" column falls in December of the prior year), so the fix has to key off each column's own embedded year rather than any single "current" year.

- [x] **`giveaway.py` crashes right after telling users there's no winner.** When `eligible_participants` is empty, it sends `"No eligible participants found."` (`cogs/giveaway.py:90-91`) but doesn't `return` — execution falls through to `winner = random.choice(eligible_participants)` on the very next line (`cogs/giveaway.py:92`), which raises `IndexError: Cannot choose from an empty sequence` on an empty list. That exception is caught by the outer `try/except`, so users see *both* "No eligible participants found." and "An error occurred: Cannot choose from an empty sequence" — confusing. **Fixed:** added the missing `return`.

- [x] **`GP_roles`' rank-threshold chain used strict `>`/`<` on every branch** (`Functions.py`, found while extracting this logic for testing), so a member's GP *exactly equal* to a threshold (1000/2500/5000/10000/25000/50000/100000) matched no branch and silently got no role at all. **Fixed:** rewritten with an inclusive lower bound, so hitting a threshold exactly now correctly grants that rank. This changes live role-assignment behavior for anyone currently sitting exactly at a threshold (in their favor — they'll now get the rank they've actually earned).

- [x] **`mygains2`'s "GP needed to rank up" had two boundary bugs** (`LedBotCode.py`, also found while extracting for testing): GP below the very first threshold silently showed "0 needed" instead of the real gap, and GP *exactly* at the top threshold (100000) showed "0 needed" instead of "You have the final rank" (only GP *strictly above* 100000 triggered that message before). **Fixed:** rewritten (sorted thresholds, explicit top-threshold check) — see `logic.compute_remaining_to_rankup`.

- [x] **`red_gp` left its GP-gained threshold undefined for any guild other than the two known ones** (`Functions.py`, also found during extraction), causing a confusing `NameError` several lines later instead of a clear error at the actual point of failure. **Fixed:** now raises a clear `ValueError` for an unrecognized guild, caught at the call site with a Discord-visible error message instead of crashing further down.

- [x] **`!giveaway`'s GP-requirement argument can silently end up comparing against SQL `NULL`.** Found while extracting `resolve_giveaway_args` for testing, not yet fixed: if a guild name is given but no GP requirement (e.g. `!giveaway <msg> #chan Aetherians`), `gp_required` stays `None` rather than defaulting to `0` — and the query later does `CAST(gp_column AS INTEGER) >= ?` with that `None`, which SQLite evaluates as `NULL`, which is never true for any row. In practice this likely means specifying a guild without also specifying a GP requirement silently disqualifies every participant. Needs a decision: should omitting the GP requirement mean "no minimum" (default to 0) regardless of whether a guild was given? **Fixed (decision made: require it explicitly).** Naming a guild without a GP number now raises `logic.GiveawayArgumentError`, which the cog reports as a plain message telling the mod to supply one (and that `0` means no minimum), rather than silently disqualifying everyone. Defaulting to `0` was considered and rejected: for a giveaway, an argument that quietly changes who can win is worse than one that asks the mod to be explicit. `""` in the guild slot is now normalized to "no guild", since downstream it already meant "both guilds".

- [x] **"Catch, print, keep going" pattern leaves several functions using undefined variables after a caught error.** In `sync_counters` (`LedBotCode.py:192-206`, `211-219`, `260-265`) and `red_gp` (`Functions.py:240-253`), failures are caught with `except Exception as e: print(...)` but execution continues into code that assumes the failed line succeeded (e.g. `rows`, `df_red_gp` never getting assigned). The result is that a DB hiccup produces a *second*, more confusing crash (`NameError`/`UnboundLocalError`) a few lines later instead of failing cleanly at the actual point of failure. **Fixed** in `sync_counters`: the failed `SELECT` now reports which table it could not read and returns, rather than falling through to a `NameError` on `rows`; and the per-member lookup `continue`s on failure instead of reusing a `discord_id` that is undefined on the first iteration and stale from the previous one after that -- that second case was worse than a crash, since it silently reported the previous member's names as though they were this one's. `red_gp` was already fixed when `filter_red_gp` was extracted.

- [x] **`except Exception: print(Exception)` loses the actual error.** In `wb_now` (`LedBotCode.py:98-100`) and `wb_next` (`LedBotCode.py:111-113`), the except block prints the literal `Exception` class object, not the caught error — so the console never shows what actually went wrong when the boss-strategy sheet fetch fails. Should be `except Exception as e: print(e)`. **Fixed:** both now bind and print the real exception, prefixed with which command failed.

- [x] **Two `conn.commit`/`conn.close` calls are missing their parentheses**, so they never actually execute — they just reference the method object and do nothing: `Functions.py:375` (`conn.commit`, should be `conn.commit()`, at the end of `GP_export`) and `LedBotCode.py:666` (`conn.close`, should be `conn.close()`, at the very end of the file). Low-impact since pandas' `to_sql` and process exit mostly cover for it, but worth fixing since it's clearly not what was intended. **Fixed:** both call the method now. Verified no other parenless `conn.commit`/`conn.close` remains anywhere in the repo.

- [x] **`kick` command can crash with no useful message.** If the given Discord ID has no row in `{Guild}_members`, `resultUID = c.fetchall()` returns `[]`, and the very next line `resultUID = resultUID[0][0]` (`LedBotCode.py:403-404`) raises `IndexError`. `kick` has no local error handler, so this hits the silent global-handler bug above. **Fixed:** an empty lookup now replies that no member with that Discord ID is assigned in the guild, and returns before the indexing.

- [x] **Blocking HTTP calls inside async command handlers.** Not from the original review -- found while working through the list. `guild_login`, `invite` and `kick` called `requests.post` directly inside `async def`, and `requests` is synchronous, so each call blocked the entire bot event loop for the length of the Firebase round trip: every other command from every user stalled behind it. **Fixed:** all three now go through a shared `post_json()` helper that runs the call in an executor, the same approach `Functions.get_cell_value` already used for its blocking Google Sheets call.

## Data safety / repo hygiene

- [x] **No `.gitignore`, and `DatabaseLedBot.db` is committed to git** (confirmed via `git ls-files`). The database contains real Discord/game member data. `service_account.json` and `.env` (bot token, guild passwords, Firebase/Sheets API keys) are currently *untracked* but nothing stops them from being swept up by a future `git add .` — there's no `.gitignore` protecting against it. **Fixed:** added `.gitignore` (`.env`, `service_account.json`, `*.db`, `venv/`, `__pycache__/`, `winners.json`, `Backups/*`) and `git rm --cached DatabaseLedBot.db`. Not purged from git history (only one commit existed; user opted to skip a history rewrite).

- [x] **`requirements.txt` is UTF-16 encoded** (likely a leftover from the PyInstaller-based `old/` build process), so `pip install -r requirements.txt` fails as-is. **Fixed:** re-saved as UTF-8. While rebuilding it for a Raspberry Pi deployment, also found and fixed a separate, more serious bug: `google-auth` and `google-api-python-client` were **completely missing** despite `Functions.py` directly importing `google.oauth2`/`googleapiclient.discovery` — the file as it existed could never have produced a working install. Also dropped Windows-only packaging tooling (`pyinstaller`, `altgraph`, `pefile`, `pywin32-ctypes`) irrelevant to running on Linux, and a duplicate `discord==2.3.1` line (`discord.py==2.3.1` already provides the `discord` module). Verified by a real `pip install -r requirements.txt` into a fresh venv followed by importing every module.

- [x] **`!backup` never attaches the backup file to Discord.** Every other export-style command (`sync_counters`, `red_gp`, `promotions`) sends the generated file back via `discord.File(...)`; `backup` (`LedBotCode.py:129-144`) just writes it to the repo root (not even into the existing `Backups/` folder) and replies `"Backup created"` with nothing attached. **Fixed:** it now calls the shared `scripts/backup_db.run_backup()` (saves into `Backups/` with a real timestamped filename) and reports that filename/failure reason in the Discord reply — deliberately still just a text confirmation, not the raw `.db` file itself, since mods never need the actual database file (it's a disaster-recovery artifact, not something anyone reads directly) and nothing in this bot's workflow should ever require SSH/filesystem access to the Pi. The weekly GP job (`GP_weekly_auto`/`!GP_weekly`) now also triggers a backup automatically right after that week's data is committed, with the same Discord confirmation — see `DEPLOY.md`.

- [ ] **Does a kicked member keep 'True Aetherian'?** Surfaced while deriving `roles_to_remove` from the rank table: the kick role-strip list contains every rank from Knight up to Primordial but not `True Aetherian`, so a kicked top-rank member keeps it while every other rank loses theirs. The derived list preserves that exactly rather than changing kick behaviour in passing. Needs a decision: is the omission deliberate, or should the top rank be stripped like the rest? If it should, the fix is dropping the `[:-1]` slice in `LedBotCode.py`.

## Tests

A `tests/` suite (pytest) now exists, covering the pieces of logic pure enough to unit test without mocking Discord/DB/network. Most of what it covers was extracted from `LedBotCode.py`/`Functions.py`/`cogs/giveaway.py` into a new side-effect-free `logic.py` module specifically to make this possible — see `logic.py`'s module docstring and `CLAUDE.md` for the architecture. Run with `pip install -r requirements-dev.txt` then `pytest` from the repo root. This is also how the four boundary/gap bugs above (`GP_roles`, `compute_remaining_to_rankup`, `filter_red_gp`, the giveaway missing-`return`) were found — writing tests for the edge cases surfaced real bugs, not just regression coverage for existing behavior. `command_error_message` is deliberately tested to *document* the still-open global-error-handler gap below, not fix it.

As a side effect, this also removed two blocks of dead code (computed a formatted string, then never used it before separately reformatting the same data by hand) that existed in both `red_gp` (`Functions.py`) and `mygains2` (`LedBotCode.py`) — both now share one `logic.format_table_block` helper instead of duplicating (and in `red_gp`'s case, half-dead-coding) the same formatting logic.

## Lower-priority / code quality

- [x] Heavy duplication between `GP_weekly_auto` (`LedBotCode.py:560-582`) and the `!GP_weekly` command (`LedBotCode.py:584-601`) — near-identical bodies that will drift out of sync if only one is updated in the future. **Fixed:** both now call a single `run_weekly_gp(ack_channel)`. `ack_channel` is the only thing that differed between the two copies -- it receives the "GP exported" acknowledgement, while the reports still always go to the mod channel, exactly as before.
- [x] Guild login (Firebase sign-in) logic is copy-pasted between `invite` and `kick` (`LedBotCode.py:317-338` and `387-396`) instead of being a shared helper. **Fixed:** both now call `guild_login(ctx, IOguild)`, which returns `(gid, id_token)` or `(None, None)` after replying with the reason. It also detects a failed sign-in, which previously fell through and sent an empty `Bearer ` token, surfacing as an unrelated failure further on.
- [x] GP role thresholds (`role_1_knight` … `role_7_true` / `GProles`) are defined twice, once each in `LedBotCode.py:33-40` and `Functions.py:31-38` — a future rank/threshold change has to remember to update both. **Fixed:** there is now one `logic.RANK_THRESHOLDS` table, with `RANK_ROLE_NAMES` and `GP_THRESHOLDS` derived from it, so the two consumers cannot disagree. This mattered more than it looked: the flat list drove the "GP needed to rank up" figure in `!mygains` while the pairs drove actual role assignment, so a threshold updated in only one file would have had the bot quoting one scale and assigning on another, silently. Pinned by tests asserting the table is ascending, that both derived lists match it, and that the two consumers agree at every boundary.
- [x] Almost all guild-specific logic branches on the literal strings `"Aetherians"`/`"Pretherians"` and builds SQL table names via f-strings (e.g. `IOguild+'_members'`) rather than a shared schema/config — error-prone to extend to a third guild and to keep in sync. **Fixed:** the guild ids, the guild list and the `{guild}_{kind}` table naming now live in `logic.py`, and every call site goes through `logic.table_name(guild, kind)`, which validates both halves. That matters beyond tidiness: a table name cannot be a bound SQL parameter, so `IOguild` -- whatever a moderator typed -- was being interpolated straight into query strings at 16 sites. `mygains` collapsed from four hand-written branches covering every combination of two guilds into a loop, and the weekly job likewise. The two real asymmetries are now named constants (`logic.RANK_ROLE_GUILD`, `logic.PROMOTION_GUILD`) so they read as domain facts rather than stragglers. The only guild literals left are the two `.env` email mappings, where the variable names are per-guild by nature.
- [x] Each module opens its own separate `sqlite3` connection (`LedBotCode.py`, `Functions.py`, and a fresh one per invocation in `cogs/giveaway.py`) without WAL mode enabled — a real risk of "database is locked" errors if two operations (e.g. the Saturday auto-run and a moderator command) touch the DB at the same moment. **Fixed (the locking half):** all four connections now set `PRAGMA journal_mode=WAL`, so a moderator command and the Saturday job no longer block each other. The connections are still separate -- consolidating them is a larger change and was left alone.
- [x] `discord.utils.get(guild.roles, name=...)` results (e.g. `role2give`, `clammy`, `aeth_duck`, `booster_duck` in `Functions.py`) are never null-checked before being passed to `add_roles`/`remove_roles` — a renamed/deleted Discord role would cause a crash instead of a clear "role not found" message. **Fixed:** the rank roles, `Monthly Top`, and the two duck roles are all null-checked now. A missing rank role skips that member with a log line, a missing `Monthly Top` skips the whole Monthly Top sync, and the duck pairing is skipped unless both of its roles resolve -- previously a missing `Aetherian Duck` would have reached `add_roles(None)` and crashed.
